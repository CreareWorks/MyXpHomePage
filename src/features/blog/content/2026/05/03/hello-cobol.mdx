# はじめに
プログラミングの設計思想を歴史から、現在のプログラミング言語との差分を見出し学びを見つけていきたいと思います。<br/>
なぜCobolなのか、という話ですがこれは深い理由はなく、私が人生で初めて触った言語が高校時代の授業で登場したCobolだったからです<br/>

ある程度、エンジニアとして経験を積んだ今、原点回帰として触ってみたいと興味が湧いたので触ってみました。<br/> 

それでは早速、簡単に環境構築の雑記から。<br/>

### Hello World を出力してみる

`hello.cbl` というファイルを作って、以下を書きます：

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. HELLO.

       PROCEDURE DIVISION.
           DISPLAY "Hello, World!".
           STOP RUN.
```

コンパイルして実行：
```bash
cobc -x hello.cbl   # -x は実行ファイルとしてコンパイル
./hello             # Hello, World!
```

#### 小ネタ
下記のように、インデントを空けずにコンパイルすると...
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. HELLO.

PROCEDURE DIVISION.
    DISPLAY "Hello, World!".
    STOP RUN.
```
下記のようなメッセージが表示されます。
```bash
cobol % cobc -x hello.cbl
hello.cbl:1: note: free format detected
    1 > IDENTIFICATION DIVISION.
    2 | PROGRAM-ID. HELLO.
    3 | 

```
これは、COBOLが**パンチカード時代の「固定形式」をデフォルトとして今も持ち続けている**ことを示しているそうです。

GnuCOBOLはインデントなしのコードを見て「あ、これは固定形式じゃないな」と判断し、自動的に**自由形式（free format）モード**に切り替えてくれます。<br/>
エラーではなく `note:` なので実行自体は成功しますが、このメッセージが出た瞬間、「形式が違うのか、、？」となったものの、特に問題なく動くので気になって調べたらどうやらCOBOLには2つの形式があるようです。<br/>

### 固定形式, 自由形式とは？

COBOLには歴史的に2つの記述形式があるようです。

**固定形式（Fixed Format）**― 1959年生まれ、パンチカード由来
```cobol
      * 列1-6: 行番号領域（今は無視）
      * 列7:   標識領域（*でコメント、-で継続）
      * 列8-11: A領域（DIVISIONやSECTION名）
      * 列12-72: B領域（実際の命令）
       IDENTIFICATION DIVISION.
       PROGRAM-ID. HELLO.
       PROCEDURE DIVISION.
           DISPLAY "Hello, World!".
           STOP RUN.
```

**自由形式（Free Format）**― COBOL 2002で標準化
```cobol
IDENTIFICATION DIVISION.
PROGRAM-ID. HELLO.
PROCEDURE DIVISION.
    DISPLAY "Hello, World!".
    STOP RUN.
```

現代の言語では「インデントに意味を持たせる（Python）」か「完全に自由（JavaScript）」かの二択ですが、COBOLは**列番号に意味を持たせる**という第三の道（もはや第一？の道？）を歩んでいました。

### なぜ列番号なのか

パンチカードは1枚80列の物理的なカードです。プログラムを修正するとき、カードを差し替えたり順番が入れ替わったりします。そこで：

- 列1〜6に**カード識別番号**を手書きして順序管理
- 列7に`*`を打てば**そのカードごとコメントアウト**
- 列73〜80は**カード名や版数**の記入欄

という運用が生まれたそうです。<br/>
物理的な制約がそのまま言語仕様になったわけです。<br/>

とは言え、パンチカードって何？って話だと思うので検索してみました。<br/>

[https://fukuno.jig.jp/1760](https://fukuno.jig.jp/1760)

こちらの記事がイメージしやすかったです、プログラミングの設計思想がハード面に依存していた時代を感じてこれだけでも面白いなぁと思いました。<br/>

## 2. 構文・言語仕様を触ってみる

COBOLの環境が整ったところで、実際にコードを書いてみます。<br/>
ここでは「変数定義」「繰り返し処理」「条件分岐」の3つを題材に、現代の言語と並べながら差分を見てみます。<br/>

---

### COBOLの4部構成

COBOLのプログラムは必ず4つの **DIVISION** で構成されます。

```cobol
       IDENTIFICATION DIVISION.   ← プログラムの名前・メタ情報
       ENVIRONMENT DIVISION.      ← 動作環境（ファイルI/Oなど）
       DATA DIVISION.             ← 変数定義
       PROCEDURE DIVISION.        ← 実際の処理
```

現代の言語でいうと、処理と変数定義が混在した1ファイルが普通だと思います。<br/>
COBOLは **「何を宣言するか」と「何をするか」を物理的に分離する** という設計になっています。<br/>

一見冗長に感じるのですが、大規模なバッチ処理を書くときに「データ定義はここだけ見ればいい」という一覧性が生まれる設計思想のようです。<br/>
当時の大型汎用機の文脈では合理的だったんだろうなと触りながら感じました。<br/>

---

### 変数定義：PIC句という独自の世界

一番最初に驚いたのが変数定義でした、

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SAMPLE-PROG.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 CUSTOMER-NAME    PIC X(30).
       01 ACCOUNT-BALANCE  PIC 9(10)V99.
       01 IS-ACTIVE        PIC X VALUE "Y".

       PROCEDURE DIVISION.
           DISPLAY "HELLO COBOL".
           STOP RUN.
```

TypeScriptで書くと：

```typescript
let customerName: string;       // 最大30文字
let accountBalance: number;     // 整数10桁 + 小数2桁
let isActive: string = "Y";
```

`PIC`（PICTURE）句というのが変数の「形」を定義する記法で、独自のミニ言語のようになっています。<br/>

| 記号 | 意味 | 例 |
|---|---|---|
| `X` | 英数字1文字 | `PIC X(30)` = 30文字の文字列 |
| `9` | 数字1桁 | `PIC 9(10)` = 10桁の整数 |
| `V` | 小数点の位置 | `PIC 9(10)V99` = 小数点以下2桁 |
| `S` | 符号あり | `PIC S9(5)` = 符号付き5桁整数 |

型推論どころか型すら存在せず、**メモリのレイアウトを直接記述している**感覚です。<br/>
`PIC 9(10)V99` は「10桁の整数部と2桁の小数部を持つ固定小数点数」という意味で、これはメモリ上の桁数を直接指定しています。<br/>
金融系のシステムで浮動小数点を使わず固定小数点で計算する、という現場の要件がそのまま言語仕様に反映されているのかなと感じました。<br/>

---

### 繰り返し処理：PERFORMとfor文

次に繰り返し処理を見てみます。1から10まで足し合わせるサンプルです。

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. SAMPLE-PROG.

       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 TOTAL   PIC 9(5) VALUE 0.
       01 COUNTER PIC 9(3) VALUE 1.

       PROCEDURE DIVISION.
           PERFORM UNTIL COUNTER > 10
               ADD COUNTER TO TOTAL
               ADD 1 TO COUNTER
           END-PERFORM.
           DISPLAY "合計: " TOTAL.
           STOP RUN.
```

Pythonで書くと：

```python
total = 0
for i in range(1, 11):
    total += i
print(f"合計: {total}")
```

`PERFORM UNTIL` は「〜になるまで繰り返す」という構文で、Pythonの `while` に近いです。<br/>
現代では `for i in range(1, 11)` と1行で書けるところが、COBOLではカウンタ変数を自分でDATA DIVISIONに宣言して、自分でインクリメントします。<br/>

ループ抽象化の歴史がここに凝縮されていて、「インクリメントを自動でやってくれる」という当たり前の便利さが、実は積み重ねられた進化だったんだと気づきました。(この時代にプログラマーをやっていた人達は大変だったんだろうなぁ)<br/>

---

### 条件分岐：IF文は意外と読みやすい

```cobol
       IF ACCOUNT-BALANCE > 1000000
           DISPLAY "優良顧客です"
       ELSE
           DISPLAY "一般顧客です"
       END-IF.
```

TypeScriptで書くと：

```typescript
if (accountBalance > 1000000) {
    console.log("優良顧客です");
} else {
    console.log("一般顧客です");
}
```

これは構造的にほぼ同じだと思います。<br/>
COBOLの「英語に近い構文」という設計思想がここに出ていて、意外と読みやすいと感じました。<br/>
括弧もセミコロンもなく、`END-IF` で閉じるスタイルは、むしろ現代のKotlinやSwiftの `if` 式に近い気もしました。<br/>

ただし `ELSE IF` は `ELSE` の中に `IF` をネストして書くのが基本で、現代の `else if` / `elif` のような糖衣構文はありませんでした。<br/>
深いネストになると一気に読みにくくなる、という点は現代の言語が解決してきた課題のひとつだと感じました。<br/>

---

### まとめ

| 項目 | COBOL | 現代言語 |
|---|---|---|
| 変数定義 | PIC句でメモリレイアウトを直接指定 | 型推論・抽象的な型システム |
| 繰り返し | カウンタを手動管理 | イテレータ・range抽象化 |
| 条件分岐 | 英語的な読みやすさ、ネストは冗長 | 糖衣構文で簡潔 |
| 構造 | 4部構成で役割を強制分離 | ファイル内に自由に混在 |

構文を触ってみると、現代言語の「便利さ」が**具体的に何を抽象化してくれているのか**が見えてきます。<br/>
型推論もイテレータも、誰かが「手動でやるのをやめよう」と決めた結果だと感じました。<br/>
COBOLはその「手動でやる前の世界」をそのまま保存しているようで時代を遡ってプログラミングを学んでいるような感覚でした。<br/>

## 3. 設計思想・アーキテクチャ

構文を触ってみると「書き方の違い」は見えてました<br/>
ただ、もう一段深く「なぜこう設計されたのか」を考えると、COBOLが生まれた1959年という時代背景を調べる必要がありました。<br/>

---

### バッチ処理という世界観

現代のシステムを思い浮かべると、ユーザーがボタンを押したらリアルタイムにレスポンスが返ってくる、というイメージが当たり前だと思います。<br/>
COBOLが生まれた1959年当時は違いました。<br/>

当時の主な用途は下記のようなものだったそうです。<br/>

- 月末に全口座の利息を一括計算する
- 夜間に当日の取引データをまとめて集計する
- 給与計算を月1回まとめて実行する

つまり「大量のデータを、決まったタイミングで、まとめて処理する」という**バッチ処理**が中心だったようです。<br/>
リアルタイムで誰かが待っているわけではないので、処理の速度より**正確さと再現性**が重要だったみたいですね。<br/>

この世界観がCOBOLの設計に直接反映されています。<br/>

```cobol
       ENVIRONMENT DIVISION.
       INPUT-OUTPUT SECTION.
       FILE-CONTROL.
           SELECT 顧客ファイル ASSIGN TO "customers.dat"
               ORGANIZATION IS SEQUENTIAL.
```

ファイルを開いて、順番に読んで、処理して、閉じる。<br/>
現代のAPIやデータベース接続とは全く違う、「ファイルを上から下へなめる」という処理モデルです。<br/>
イベント駆動も非同期処理も存在しない、直列の世界です。<br/>

---

### ファイル中心の設計 vs 現代のデータ層

COBOLが扱うデータの基本単位は**ファイル**だったようです。<br/>
当時は `VSAM`（Virtual Storage Access Method）や順編成ファイルといった形式で、今でいうRDBやNoSQLとは全く異なる概念でした。<br/>

現代のWebアプリを例にすると、こんな対比になります。<br/>

| やりたいこと | COBOL時代 | 現代 |
|---|---|---|
| データの保存 | 順編成ファイル / VSAM | RDB / NoSQL |
| 特定レコードの取得 | ファイルを先頭から順に読む | SQLのWHERE句、インデックス検索 |
| 複数システム連携 | JCL（ジョブ制御言語）でファイルを受け渡し | REST API / メッセージキュー |
| トランザクション | プログラムが手動で整合性を担保 | DB側のACIDトランザクション |

SQLの `WHERE id = 123` で一発で取れるレコードを、COBOLではファイルの先頭から順番に読んで比較しながら探していました。<br/>
インデックスという概念をデータベース側が持つようになったのは、その後の大きな進化のひとつです。<br/>

---

### 「英語で読める」という思想

COBOLの設計者のひとりである[グレース・ホッパー](https://ja.wikipedia.org/wiki/%E3%82%B0%E3%83%AC%E3%83%BC%E3%82%B9%E3%83%BB%E3%83%9B%E3%83%83%E3%83%91%E3%83%BC)は、**プログラムは人間が読める言語で書けるべきだ**という強い信念を持っていました。<br/>
こういう設計思想を含めて、今のAIが台頭してきた現代から見るととても時代を感じる思想だなとある種ロマンというか、時代の移ろいを感じました。<br/>

```cobol
       MULTIPLY UNIT-PRICE BY QUANTITY GIVING TOTAL-AMOUNT.
       IF TOTAL-AMOUNT IS GREATER THAN 100000
           MOVE "優良取引" TO TRANSACTION-TYPE
       END-IF.
```

`MULTIPLY ... BY ... GIVING ...` や `IS GREATER THAN` など、英語の文章に近い構文を意識して設計されています。<br/>
当時のターゲットユーザーは「プログラマー」ではなく、**経理や業務担当者が読んで内容を確認できること**も想定していたとされています。<br/>

これは今の視点から見ると非常に興味深い発想で、現代でいうとSQLやHCL（TerraformのDSL）に近い思想だと感じました。<br/>

```sql
SELECT * FROM orders WHERE total_amount > 100000;
```

```hcl
resource "aws_instance" "web" {
  instance_type = "t3.micro"
}
```

SQLもHCLも「何をするか」を宣言的・英語的に記述する言語です。<br/>
COBOLはその先駆けとして、**ドメイン専門家が読めるコード**を目指していたわけです。<br/>
現代のDSLやIaCツールが目指していることと、実は根っこが繋がっているように感じました。<br/>

---

### 変わらなかったもの：ビジネスロジックの複雑さ

設計思想を見ていくと「現代は進化した」という話ばかりになりがちですが、変わっていないものもあります。<br/>

**ビジネスロジックの複雑さ**です。<br/>

消費税の計算ひとつとっても、軽減税率があり、端数処理のルールがあり、業種によって例外があると思います。<br/>
給与計算なら社会保険料の控除ルール、扶養人数による変動、年末調整の計算があります。<br/>
これらは1959年も2026年も本質的には変わっていません。<br/>

COBOLで書かれた金融・行政システムが今も動き続けている理由は、**何十年もかけて積み上げられたビジネスロジックそのもの**が資産として残っているからだと思います。<br/>
言語を変えることは、コードを書き直すことではなく、そのロジックを一から再検証することを意味します。<br/>

構文やアーキテクチャは時代とともに変わっても、「複雑な現実をコードで表現する難しさ」は変わっていないと感じました。<br/>

## 4.現場での現役稼働（金融・行政）

構文を触り、設計思想を理解したところで、なぜ2026年になってもCOBOLが動いているのかを考えてみます。<br/>

---

### 数字で見るCOBOLの現在地

「COBOLはもう古い」というイメージがある一方で、現実の数字は全く違う景色を示しています。<br/>

ガートナーの調査によれば、全プログラム約3,100億行のうち約65%にあたる約2,000億行がCOBOLで書かれており、毎年約50億行が増え続けているとされています。（出典：[COBOL - Wikipedia](https://ja.wikipedia.org/wiki/COBOL)）<br/>

IBMによれば、COBOLは対面でのクレジットカード取引の80%をサポートし、すべてのATM取引の95%を処理し、毎日30億ドル以上の商取引を生み出すシステムを支えています。（出典：[COBOLとは | IBM](https://www.ibm.com/jp-ja/think/topics/cobol)）<br/>

フォーチュン500企業の90%がCOBOLプログラムを使い続けており、世界のトランザクション処理システムの70%でCOBOLが利用されているとも言われています。（出典：[COBOL - Wikipedia](https://ja.wikipedia.org/wiki/COBOL)）<br/>

「古い技術の話」ではなく、**今この瞬間も世界中の送金・給付・税務計算を支えている技術**というのが実態です、AIによって簡単にコードが生成される今、COBOLのコードが何十年も渡って今もなお生き続けているというのは、ある種のロマンを感じます。<br/>

※ソースがWikipediaですみません、明後日の話をしていたら申し訳ございません。

---

### 日本の金融システムについて

日本で特に象徴的なのが**みずほ銀行の勘定系システム**だと思います。<br/>

みずほ銀行は2002年の合併時にシステム統合に失敗し、大規模な障害を起こしたことは有名です。<br/>
その後、旧第一勧業銀行・富士銀行・日本興業銀行の3系統のシステムを抱えたまま運用を続け、完全な統合・刷新が完了したのは**2019年**のことでした。<br/>

プロジェクトの規模は、新勘定系システム「MINORI」の開発だけで**投資額4,000億円台半ば、開発期間約8年**。<br/>
合併発表の1999年から数えると**20年越しの悲願達成**でした。（出典：[みずほFGが勘定系システム「MINORI」をリニューアル | 日経クロステック](https://xtech.nikkei.com/atcl/nxt/column/18/00001/10837/)）<br/>

「なぜもっと早く刷新しなかったのか」という問いに対する答えは、調べて学んでみると少し理解できます。<br/>
ビジネスロジックの複雑さはコードの行数だけでは測れません。<br/>
何十年もかけて現場の例外処理や業務ルールが積み重なったシステムを、動かしながら置き換えるのは、エンジニアとして想像もしたくないような苦労の絶えない作業だったと想像します。<br/>

---

### 行政システムも同じ構造


金融だけでなく、行政システムも同様です。<br/>

給与計算、年金基金、銀行や保険会社のシステムといった行政・金融インフラの多くが、メインフレーム上のCOBOLで動いてきました。（出典：[レガシーシステムモダン化と、生き続けるCOBOLのリアル | IPA DX SQUARE](https://dx.ipa.go.jp/modernization_cobol)）<br/>

年金システムを例にとると、現行の年金給付システムは1964年度、記録管理システムは1984年度にそれぞれ稼働しており、長年メインフレームを中心に運用されてきました。 <br/>
厚生労働省・日本年金機構による刷新プロジェクトでも、現行システムがメインフレームに深く依存しており、他事業者の参入が困難なベンダーロックイン状態が続いてきたことが課題として明記されています。（出典：[新たな年金業務システムの構築について | 厚生労働省](https://www.mhlw.go.jp/content/12508000/001044796.pdf)）<br/>

マイナンバーシステムの構築にあたっても、既存の行政システムとの連携が設計の前提となっており、行政機関等の間での情報連携により各種行政手続の添付書類省略を実現する仕組みとして整備されています。（出典：[マイナンバー制度とは | デジタル庁](https://www.digital.go.jp/policies/mynumber/explanation)）<br/>

行政システムの特性として、**一度でも誤った計算をすると市民の生活に直接影響する**という点があると思います。<br/>
金融もそうですが、「動いているものへの信頼」はコードの綺麗さよりも優先されます。<br/>
新しいアーキテクチャへの移行は、技術的な正しさよりも**リスクの低さ**で判断されるんだろうなと感じました。<br/>

### 「動いているものは触るな」の合理性

現在稼働しているCOBOLシステムの多くは、**書いた人間がもういない**という状況にあります。<br/>
ドキュメントも不完全で、なぜそのロジックになっているのかの文脈が失われているコードが大量にあります。<br/>
そういったコードを「動いている」という事実だけを根拠に信頼し続けることは、ある意味で合理的な判断だと思います。<br/>

変更を加えた瞬間に、誰も気づいていなかった副作用が顕在化するリスクがある。<br/>
テストを書くにも、正解がわからない。<br/>
これは技術的負債と呼べるものだとは思いますが、「だから触らない」という判断は、ある意味で合理的な判断だと思います。<br/>

## 5.まとめ

COBOLを環境構築から触り、構文を書き、設計思想を読み、現役稼働の現実を見てきました。<br/>
最後に、この一連の体験から見えてきたことを整理します。<br/>

### 現代の「当たり前」は、誰かが解決した課題

COBOLを調べていると、現代の言語がいかに多くのことを「やってくれている」かに気づきます。<br/>

型推論は、PIC句でメモリレイアウトを手書きしていた時代の先にあります。<br/>
イテレータは、カウンタ変数を自分で宣言してインクリメントしていた時代の先にあります。<br/>
ORMは、ファイルを先頭から順番になめて比較していた時代の先にあります。<br/>
CI/CDは、コンパイルして手動で実行ファイルを配置していた時代の先にあります。<br/>

どれも「あって当たり前」に感じている機能ですが、COBOLを触るとその一つひとつに「誰かがこれを面倒だと思って、解決した」という痕跡が見えます。<br/>
抽象化の積み重ねが現代の開発体験を作っていると、頭でわかっているのと、手で感じるのとでは全然違いました。<br/>

---

### 変わらなかったもの

一方で、60年経っても変わっていないものもあると思います。<br/>

ひとつは**ビジネスロジックの複雑さ**です。<br/>
消費税の軽減税率、給与計算の控除ルール、金融商品の利息計算。これらは1959年も2026年も本質的には変わっていません。COBOLで書かれたコードが今も動き続けている最大の理由は、言語ではなく、**その中に積み上げられたビジネスロジックそのものが資産だから**です。<br/>

もうひとつは**人間が読めるコードへの要求**です。<br/>
COBOLが英語に近い構文を目指した理由は、「業務担当者が読めること」でした。それは今でいうDSLやIaCの思想と繋がっていて、「コードは実行されるだけでなく、人間に読まれるものだ」という価値観は変わっていません。<br/>
可読性への要求はむしろ現代の方が強くなっていて、コードレビューや命名規則への関心の高さはその表れだと思います。<br/>

---

### 「レガシー」という言葉について

COBOLを調べるまでは、「レガシーシステム」という言葉をどこかネガティブな印象がありました。<br/>
古い、負債、早く捨てるべきもの、という文脈です。<br/>

でも触って調べてみると、少し見方が変わりました。<br/>

動き続けているシステムには、それだけの理由があります。<br/>
ビジネスロジックの複雑さ、移行リスク、積み上げられた信頼。<br/>
それらを理解せずに「古いから置き換えるべき」と言うのは、現場の文脈を無視した話です。<br/>

---

### 最後に：原点回帰で見えたこと

高校の授業でCOBOLに触れてから、エンジニアとしてのキャリアを積んできました。<br/>
その間に使ってきた言語やフレームワークは変わり続けましたが、COBOLを再び触ってみて、**変化の速さに慣れてしまっていたこと**に気づきました。<br/>

新しいものが出るたびに乗り換えることは簡単です。<br/>
でも、なぜ今の設計になっているのかを理解するには、その前の世界を知ることが早道だと思います。<br/>

COBOLは過去の遺物ではなく、現代のプログラミングがどこから来たのかを教えてくれる言語でした。<br/>
一周回って触ってみて、良かったと思っています。<br/>
